# Hermes Pilot Validation

Hermes was installed externally and live zero-tool planning requests were attempted using the official `hermes chat --quiet --query` path, `--safe-mode`, a one-turn limit, the official empty `context_engine` toolset, `openrouter`, and `openai/gpt-oss-safeguard-20b`. One request reached the model and returned a five-step research proposal with matching task ID and only pilot capability IDs, with zero tool calls. It was not a valid JARVIS protocol response: it included extra top-level request/metadata fields and omitted required status, summary, skill, operation, permission, risk, confirmation, reversibility, success, and failure-strategy fields. Strict validation rejected it. The exact-schema retry returned HTTP 429 from upstream provider Groq. No plan was accepted and no JARVIS action, file, background task, or speech output was created.

The JARVIS-side protocol, adapter, health, task, settings, and Colibri tests pass. The full suite reports 587 collected, 587 passed, 0 failed, and 0 skipped. The protocol rejects malformed or schema-incomplete JSON, blocked capabilities, and shell text; task records support pause, resume, cancellation, and a two-task concurrency bound. The prompt now states the exact response contract without relaxing validation. UTF-8 output is decoded explicitly, decorated CLI output is never parsed, and every real attempt left zero Hermes processes and no listener on port 9119. The adapter reads only the exact failed session's safe status/body metadata and reports `429` and upstream provider without exposing private identifiers or secrets. Deterministic blocking-process regressions prove stop/emergency cancellation and timeout terminate and clear the exact adapter-owned request. GUI settings use only supported runtime modes and keep background, schedule, and learning controls locked off.

Live Hermes plan acceptance, Hermes-driven Word output, real GUI Hermes progress, Piper completion speech for a Hermes task, and a live-provider emergency interruption remain unvalidated because no response has passed the exact schema and the strict-schema retry was rate-limited. JARVIS's cancellation fan-out and adapter interruption boundary are independently validated. A future retry remains safe only through the constrained adapter and only after provider capacity returns.
