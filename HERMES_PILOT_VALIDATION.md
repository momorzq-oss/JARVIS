# Hermes Pilot Validation

Hermes was installed externally and live zero-tool planning requests were attempted using the official `hermes chat --quiet --query` path, `--safe-mode`, a one-turn limit, the official empty `context_engine` toolset, `openrouter`, and `openai/gpt-oss-safeguard-20b`. One request reached the model and returned a five-step research proposal with matching task ID and only pilot capability IDs, with zero tool calls. It was not a valid JARVIS protocol response: it included extra top-level request/metadata fields and omitted required status, summary, skill, operation, permission, risk, confirmation, reversibility, success, and failure-strategy fields. Strict validation rejected it. Five later exact-schema requests returned HTTP 429 from upstream provider Groq, including bounded retries on 2026-07-23. No plan was accepted and no JARVIS action, file, background task, or speech output was created.

The JARVIS-side protocol, adapter, health, task, settings, and Colibri tests pass. The full suite reports 704 collected, 704 passed, 0 failed, and 0 skipped. The protocol rejects malformed or schema-incomplete JSON, blocked capabilities, shell text, planned responses with no steps, capabilities outside the exact per-request subset, and permission/risk metadata that contradicts the supplied registry record. The orchestrator now derives exposure only from healthy connected JARVIS registry records: 13 pilot capabilities are currently eligible, including the real `research.search_web`, `research.read_source`, and `research.summarize_sources` adapters. Public source reads reject local/private network destinations. Task records support verified progress/output, pause, resume, atomic cancellation, policy-bounded retry, confirmation records, and a two-task concurrency bound; returned records are mutation-isolated snapshots, impossible state transitions are rejected, and progress cannot exceed the declared plan. A third active request is rejected before a provider call. The trusted executor fails closed unless a step returns an explicit verified status. The prompt states the exact response contract without relaxing validation. UTF-8 output is decoded explicitly, decorated CLI output is never parsed, and every real attempt left zero Hermes planning processes and no listener on port 9119. The adapter reads only the exact failed session's safe status/body metadata and reports `429` and upstream provider without exposing private identifiers or secrets. Deterministic blocking-process regressions prove stop/emergency cancellation and timeout terminate and clear the exact adapter-owned request, including cancellation during retry-state updates. GUI confirmation timing is deterministic under event-loop delay: the visible Qt timer owns the deadline and the worker waits a bounded delivery grace. Simultaneous requests are queued through one serialized confirmation channel and receive independent decisions; shutdown safely rejects active and queued requests. Mission Control and task-control commands share one deterministic current-task selector, including when multiple active tasks exist or only terminal history remains. GUI settings use only supported runtime modes, enforce strict approval and a two-task maximum, keep background/schedule/learning controls locked off, and deliver the real runtime snapshot from a worker thread. Live source validation displayed Hermes Agent v0.19.0 and its real install/version details while the dialog remained responsive. The shared typed/voice route now handles flexible Hermes status, task-list, planning, pause, resume, cancel, approve, deny, `/goal`, and `/background` commands. `/background` produces a reviewable plan only; APPROVE ONCE runs it interactively. Valid plans persist by task ID until one explicit terminal decision and cannot execute twice. Mission Control shows the safe summary and requested capability IDs, enabling APPROVE ONCE and DENY only for a real retained plan. Live tests returned the real disabled state and install path, showed zero recorded tasks, rejected planning without creating a task or provider call, preserved local time conversation, issued exactly one Piper synthesis request for each response, and displayed disabled approval controls when no plan exists. Metadata-only audit events link the task, provider/model, filtered capability IDs, plan hash, decisions, steps, retries, cancellations, redacted output paths, and terminal state without logging goals, requests, parameters, or results.

Live Hermes plan acceptance, Hermes-driven Word output, real GUI Hermes progress, Piper completion speech for a Hermes task, and a live-provider emergency interruption remain unvalidated because no response has passed the exact schema and the strict-schema retries were rate-limited. JARVIS's cancellation fan-out and adapter interruption boundary are independently validated. A future retry remains safe only through the constrained adapter and only after provider capacity returns.

The source runtime was also restarted through the real Desktop shortcut on 2026-07-23. It painted the main window in 2.7 seconds, loaded the `hey_jarvis` model, opened the configured USB microphone, completed one Piper greeting, showed no visible console window, and reopened the real Settings dialog. A preceding controlled exit closed voice and the microphone and left the Qt event loop with code 0. A later live emergency-button test interrupted active Piper playback with no completion event, released input, discarded pending commands, left JARVIS responsive, and restored the visible `LISTENING WAKE` state. The production executable and existing recovery candidate were not modified.
