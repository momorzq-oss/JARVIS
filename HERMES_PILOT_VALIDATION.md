# Hermes Pilot Validation

Hermes was installed externally and live zero-tool planning requests were attempted using the official `hermes chat --quiet --query` path, `--safe-mode`, a one-turn limit, the official empty `context_engine` toolset, `openrouter`, and `openai/gpt-oss-safeguard-20b`. One request reached the model and returned a five-step research proposal with matching task ID and only pilot capability IDs, with zero tool calls. It was not a valid JARVIS protocol response: it included extra top-level request/metadata fields and omitted required status, summary, skill, operation, permission, risk, confirmation, reversibility, success, and failure-strategy fields. Strict validation rejected it. Three later exact-schema requests returned HTTP 429 from upstream provider Groq, including bounded retries on 2026-07-23 at 13:58 and 14:25 Asia/Dubai. No plan was accepted and no JARVIS action, file, background task, or speech output was created.

The JARVIS-side protocol, adapter, health, task, settings, and Colibri tests pass. The full suite reports 624 collected, 624 passed, 0 failed, and 0 skipped. The protocol rejects malformed or schema-incomplete JSON, blocked capabilities, and shell text; task records support pause, resume, cancellation, and a two-task concurrency bound. The prompt now states the exact response contract without relaxing validation. UTF-8 output is decoded explicitly, decorated CLI output is never parsed, and every real attempt left zero Hermes processes and no listener on port 9119. The adapter reads only the exact failed session's safe status/body metadata and reports `429` and upstream provider without exposing private identifiers or secrets. Deterministic blocking-process regressions prove stop/emergency cancellation and timeout terminate and clear the exact adapter-owned request. GUI settings use only supported runtime modes and keep background, schedule, and learning controls locked off.

Live Hermes plan acceptance, Hermes-driven Word output, real GUI Hermes progress, Piper completion speech for a Hermes task, and a live-provider emergency interruption remain unvalidated because no response has passed the exact schema and the strict-schema retries were rate-limited. JARVIS's cancellation fan-out and adapter interruption boundary are independently validated. A future retry remains safe only through the constrained adapter and only after provider capacity returns.

The source runtime was also restarted through the real Desktop shortcut on 2026-07-23. It painted the main window in 2.7 seconds, loaded the `hey_jarvis` model, opened the configured USB microphone, completed one Piper greeting, showed no visible console window, and reopened the real Settings dialog. A preceding controlled exit closed voice and the microphone and left the Qt event loop with code 0. A later live emergency-button test interrupted active Piper playback with no completion event, released input, discarded pending commands, left JARVIS responsive, and restored the visible `LISTENING WAKE` state. The production executable and existing recovery candidate were not modified.
